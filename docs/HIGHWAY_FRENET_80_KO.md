# test/rrt 고속도로 제어 — 2026-10-08 개편

기존 고속도로 전략 노드의 RRT/누적 보정/전역 경로 복귀 로직을 단일 목표 차로
제어로 교체했다. 일반 주행, 카메라 모델, 신호등·보행자·회전교차로의 독립 정지
입력은 유지한다. 기존 RRT 및 이전 전략 내부 함수에 의존하던 테스트는 삭제하고
새 제어의 요구사항과 폐루프 주행을 검증하는 테스트로 대체했다.

## 실행

ROS가 설치된 **기존 실행 환경 안에서** 저장소를 갱신하고 워크스페이스를 빌드한다.
Docker로 실행 중이면 해당 컨테이너 안에서 수행한다. VirtualBox Ubuntu에 ROS를
직접 설치해 사용 중이면 그 Ubuntu 터미널에서 수행한다.

```bash
cd ~/morai_ws/src/ROI
git switch test/rrt
git pull --ff-only origin test/rrt
cd ~/morai_ws
source /opt/ros/noetic/setup.bash
catkin_make
source devel/setup.bash
roslaunch purepursuit_mgeo highway.launch
```

실제 워크스페이스가 `~/catkin_ws`이면 위의 `~/morai_ws`만 그 경로로 바꾼다.
`git switch` 또는 `pull`이 로컬 변경 때문에 거절되면 먼저 저장소 안에서
`git stash push -u -m "before-highway-rebuild"`로 보관하고 다시 진행한다.
보관한 이전 제어 수정은 새 코드에 자동으로 다시 적용하지 않는다.

- 기본 목표: `target_speed_mps:=22.222222` = **80 km/h**.
- 시뮬레이터 Host IP: `192.168.0.147`, 코드 PC의 수신 IP: `192.168.0.185`.
- 차선 카메라 수신 포트: **1101**, YOLO 카메라 수신 포트: **1131**.
- Competition Vehicle Status: **9080 / 9081**, Ego Ctrl Cmd: **9093 / 9094**.
- 전체 실행은 위의 roslaunch 하나로 한다. 카메라 노드를 다른 터미널에서 중복 실행하지 않는다.
- 별도 값이 필요하면 예를 들어 `target_speed_mps:=5.0`을 roslaunch 뒤에 붙인다.

## 판단과 경로

고속도로 활성화 입력은 기존 YOLO 차량 검출 기반 환경 게이트를 사용한다.
활성화됐다는 사실만으로 차선 변경이 시작되지는 않는다. 최근 카메라 경계와
LiDAR 추적 객체, 위치 입력이 있어야 한다.

1. 카메라의 **실제 좌우 경계 중점**을 사용한다. 한쪽 경계 추정, HELD 결과,
   차선을 밟는 상태, 두 차로를 합친 폭은 변경 허가에 사용하지 않는다.
2. 관측 시각의 차량 자세로 경계를 지도 좌표에 옮긴다. 차량이 왼쪽으로 조향해도
   도로 기준축과 목표 차로가 함께 왼쪽으로 돌아가지 않는다.
3. 도로 방향 거리 `s`와 횡방향 거리 `d`를 쓰는 Frenet 좌표에서 왼쪽 인접 차로의
   중심 **하나만** 목표로 정한다. 외측 경계가 보이면 목표 차로 폭을 측정하며,
   그렇지 않으면 측정된 현재 차로 폭과 같은 평행 차로로 가정한다.
4. `d(s)`를 5차 다항식으로 생성한다. 시작 위치·방향을 연결하고 도착점의 횡방향
   기울기와 2차 미분은 0으로 둔다. 종점 이후 경로는 목표 차로와 평행하게 이어진다.
5. 경로 길이는 실제 속도와 횡가속도·횡저크 예산으로 결정한다. 80 km/h, 3.5 m
   차로 기준 약 **97 m / 4.4초**다. 조향을 크게 주어 급히 가로지르는 방식이 아니다.
6. 앞·뒤 차량의 상대속도와 변경 소요시간을 반영한 공간을 확인한다. 앞차 추종으로
   변경 중 속도가 낮아져 뒤차가 더 가까워질 가능성도 검사한다. 전체 경로를
   이동 장애물 경계 상자와 비교한다. 통과 가능한 조건이 0.25초 및 서로 다른
   LiDAR 관측 3개 이상 유지되면 변경을 시작한다.
7. 변경 중 목표는 고정한다. 카메라가 다음다음 차로를 골라도 목표가 옮겨가지 않는다.
   완료에는 실제 위치 오차 **22 cm 이내**, 도로 대비 yaw 오차 **1.5도 이내**,
   계획 종점 도달, 목표 차로의 최근 경계 확인이 모두 필요하다.
8. 변경 완료 후 중앙과 방향을 유지한 상태로 **최소 5초** 주행해야 다음 변경을 허용한다.
   이 시간이 지나도 정렬·점선·공간 조건이 만족되지 않으면 현재 차로를 유지한다.

Frenet은 좌표계이고, 5차 다항식은 그 좌표계에서 경로를 만드는 수식이다.
두 가지를 함께 사용한다. 임의 표본 트리를 만들거나 여러 차로 후보를 탐색하지 않아
경로 생성은 일정한 계산량을 가지며, 충돌 검사는 객체 수와 경로 샘플 수에 비례한다.

## 마지막 차로와 중앙 추종

현재 차로의 **가장 가까운 왼쪽 경계가 실선, 오른쪽 경계가 점선**이면 새로운
변경을 즉시 금지한다. 해당 차로와 일치하는 연속 3개 관측으로 확인하면 `LOCKED`를
유지한다. 이후 점선으로 잠깐 오분류돼도 다시 변경하지 않는다. 실선은 정지 사유가 아니다.

진입부 복합선은 실선과 점선의 기하가 공통 관측 구간 8 m 이상에서 20 cm 이내로
겹칠 때만 인정한다. 오른쪽이 실선인 진입 차로에서만 이 복합선을 변경 허가에
사용한다. 오른쪽이 점선인 마지막 차로의 실선 금지가 우선한다.

고속도로 횡제어는 경로 곡률 선행 보상과 횡방향 오차·방향 오차 피드백을 사용한다.
차로 중심 오프셋은 주지 않는다. 카메라 관측을 도로 좌표에서 완만하게 반영하고,
조향 변화율과 횡가속도를 제한한다. 변경 경로의 유한한 끝을 목적지로 오인해
정지하지 않도록 매 주기 앞으로 이어지는 경로를 발행한다. 고속도로 진입 후에는
바깥쪽 전역 경로로 돌아가는 기존 로직을 사용하지 않는다.

## 앞차 추종과 제동

LiDAR 객체를 도로 좌표에 투영해 자차 차로/진행 경로와 겹치는 전방 객체만 고른다.
뒤차와 옆 차로 차량은 단지 가까이 있다는 이유로 앞차가 되지 않는다. 변경 중에는
가까운 미래에 실제 이동 경로와 겹치는 앞차도 고려한다.

기본 목표 차간거리는 `5 m + 1.5초 × 자차 속도`다. 앞차의 도로 방향 속도에
차간거리 오차에 비례하는 값을 더해 목표 속도를 정한다. 가감속과 그 변화율을
제한하고 고속도로용 PI 속도 제어를 사용해 목표 변경 시 미분항의 급제동을 피한다.
앞차가 없어지면 설정한 순항 속도로 회복한다. 곡률이 큰 도로에서는 횡가속도
예산에 맞게 속도를 낮춘다.

뒤차는 **변경 시작 전 공간 판단**에 사용한다. 변경 후 뒤차가 가까워졌다는 사실을
전방 제동 조건으로 사용하지 않는다. 다만 실제 전방 충돌 임박, 센서·명령 timeout,
신호등·보행자 등 독립적인 정지 조건은 제동할 수 있다. 이전의 고속도로 무조건
제동 무시 옵션은 최종 UDP 송신 단계에서도 제거했다.

고속도로 실행에서는 LiDAR 소프트웨어 관심 영역을 전방 80 m, 후방 80 m,
좌우 16 m로 전달한다. 이 설정은 센서의 실제 검출 성능이나 가림을 보장하지 않는다.

## 상태 확인

RViz 기본 화면에 `Highway Controller State`와 노란색 실제 제어 경로를 추가했다.
기존 LiDAR의 공간 가능 표시는 전략 노드의 변경 시작을 뜻하지 않는다.

| 상태 | 의미 |
|---|---|
| `OFF` | 일반 전역 경로/장애물 회피 출력 사용 |
| `ACQUIRE` | 고속도로 활성화 후 유효한 차로 관측 대기 |
| `HOLD` | 차로 중앙 정렬 또는 5초 유지 |
| `WAIT_GAP` | 왼쪽 변경 조건은 만족, 안전 공간 확인 중 |
| `CHANGE` | 고정된 한 차로 변경 경로 추종 |
| `SETTLE` | 종점에 도착했지만 위치·yaw 정렬을 더 확인 |
| `LOCKED` | 마지막 허용 차로에서 중앙 추종, 추가 변경 금지 |

상태 JSON은 `/highway_lane_strategy/state`에 발행한다. `reason`, 차로 중심 오차,
yaw 오차, 변경 횟수, 센서 나이, 앞차 ID·거리·속도, 공간을 막는 객체 ID를 포함한다.
`lane_geometry_stale`, `lidar_stale`, `odometry_stale`는 실선과 별개의 센서 문제다.

## 검증 범위

순수 Python 회귀 테스트와 ROS 메시지 어댑터 모의 테스트로 80 km/h 연속 두 번의
한 차로 변경, 5초 유지, 마지막 차로 잠금, 카메라 위치·방향·곡률 잡음, 0.25초 지연,
0.15초 조향 지연, 잘못된 인접 차로 관측, 완만한 곡선, 앞차 추종 및 rear/side
오검출 제동 방지를 검사한다. UDP 제동 전달과 launch 범위 전달도 검사한다.

```bash
PYTHONPATH=src/control/purepursuit_mgeo/src:src/control/path_planning/src \
python3 -m unittest discover -s src/control/purepursuit_mgeo/test -v
```

현재 검증은 합성 센서와 차량 운동 모델에 기반한다. 실제 MORAI에서 새 버전을
실행한 결과는 아직 없다. 카메라 보정 오차, 프레임 처리 속도, 실제 조향 응답,
LiDAR 가림·미검출·추적 오차까지 제거되었다는 뜻은 아니다. 객체는 등속도로
예측하며 차로는 짧은 구간의 일정 곡률로 근사한다. 충돌 없는 주행을 보장하는
검증 결과로 해석해서는 안 된다.

핵심 코드: `src/control/purepursuit_mgeo/src/purepursuit_mgeo/highway.py`.
ROS 연결: `scripts/highway_lane_strategy_node.py`.
최종 횡·종 제어 연결: `scripts/purepursuit_mgeo_node.py`.
